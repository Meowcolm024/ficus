# Ficus trade-offs

Ficus is an opinionated, minimalist scripting language with global Hindley–Milner inference. These omissions keep that goal manageable; they are design choices, not claims that richer languages are inferior. [SPEC](SPEC.md) defines the actual rules.

## Restricted traits instead of general implicit search

Ficus chooses Haskell 98-ish, single-parameter traits over the wider machinery of [modern GHC type classes](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/instances.html), [Agda instance arguments](https://agda.readthedocs.io/en/stable/language/instance-arguments.html), or [Scala implicit resolution](https://docs.scala-lang.org/scala3/reference/changed-features/implicit-resolution.html). Restricted implementation heads, decreasing instance constraints, acyclic supertraits, and rejection of overlap make resolution terminating and deterministic for accepted programs. Ownership rules preserve coherence across modules. The aim is predictable inference and diagnostics without search priorities, backtracking heuristics, or results that depend on local implicit scope. This sacrifices expressive instance relationships and contextual customization; it does not imply that every richer system is undecidable or nondeterministic. [The Implicit Calculus: A New Foundation for Generic Programming](https://doi.org/10.1145/2345156.2254070) gives a formal model of implicit resolution, including higher-order rules and partial resolution. See the [Haskell 98 report's class and instance restrictions](https://www.haskell.org/onlinereport/decls.html).

The library keeps `Functor`, `Pure`, `Seq`, and `Bind` independently usable, with `Applicative` and `Monad` bundling capabilities. This makes constraints precise, at the cost of more traits and explicit implementations. `Seq` and alternative choice take explicit thunks for their second operands, so an instance can skip work without changing strict call semantics. Callers must write the thunk; operator syntax does not insert it or provide memoization. Derived helpers stay outside trait dictionaries because Ficus has no default methods.

A concrete precedent is [Lean's `Seq`](https://github.com/leanprover/lean4/blob/master/src/Init/Prelude.lean), whose second operand has type `Unit → f α`, and its [Alternative API](https://github.com/leanprover/lean4/blob/master/src/Init/Control/Basic.lean), which delays the right-hand choice in the same way. Lean documents `Option` choice as selecting the first success. Ficus adopts those delayed API arguments, but keeps the thunk explicit in ordinary calls and operators.

## A small inference system instead of richer type relations

Ficus omits nominal, structural, and row-based subtyping, GADTs, and dependent types to preserve its simple global inference model. Subtyping needs inequality constraints and variance; [GADTs](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/exts/gadt.html) introduce branch-local type equalities; dependent types require reasoning about terms inside types. Supporting these can require a different solver, more annotations, or restricted inference. Ficus still has nominal ADTs and structural products and lists; those do not imply subtyping.

Parenthesized pattern annotations constrain inference without adding type-pattern matching. In v0, `foo (x : Int) = x` is valid, while `foo (x : a) = x` cannot implicitly introduce or capture a named type variable. Alias and other type parameters may have kind annotations, but still bind names rather than match concrete types. This keeps scope explicit at the cost of restricting polymorphic argument annotations. The draft `foo {a} (x : a) = x` would require an explicit type binder; it does not by itself introduce dependent types. Type literals are excluded. Ordinary record updates preserve the receiver's full type rather than permitting type-changing replacement; labels do not infer a nominal record identity. This simplifies inference but prevents using an update to change a record's type arguments.

Existential record type members are targeted for v1+, with witness scope and non-escape checks. They offer hidden representations without full dependent types, but add checking and unpacking rules. Type members are excluded from the draft positional constructor slots; positional matching may be rejected for existential records. That choice, and updates of existential records, remain open, rather than treating type members as ordinary value patterns.

There are also decidability limits: in full System F with bounded subtyping (`F_<:`), both subtyping and typing are undecidable. See Pierce's [Bounded Quantification Is Undecidable](https://doi.org/10.1006/inco.1994.1055). This result concerns that combination of subtyping and bounded polymorphism, not every subtyping system.

This is not a claim that subtyping rules out principal types: Boolean-algebraic types combine unions, intersections, and negation; carefully designed systems can retain principal inference. See [The Simple Essence of Boolean-Algebraic Subtyping](https://doi.org/10.1145/3776689). Ficus chooses the smaller solver and simpler inferred types instead.

## File modules instead of an ML module calculus

Ficus uses file-based modules and imports, without ML-style signatures, functors, or first-class modules (see [OCaml modules](https://ocaml.org/docs/modules) for a concrete example). Those features support powerful abstraction, but add another language of composition and checking. For simple scripts, ordinary functions, ADTs, and traits are the intended tools. Planned libraries and dependency resolution do not require an ML module calculus.

## Strict evaluation and the cost of recursion

Haskell's laziness makes infinite structures and tying recursive knots convenient, but it can also retain unevaluated work and the data that work refers to. Space leaks can make memory use difficult to predict; see [Space Improvements and Equivalences in a Functional Core Language](https://doi.org/10.4204/EPTCS.265.8). Ficus chooses strict, left-to-right evaluation so ordinary computation and effects happen when their expressions are evaluated. Strictness does not eliminate every space leak, and it can evaluate work that laziness would avoid.

The cost is less freedom in recursive value definitions. Ficus permits mutually recursive functions, but every reference within a recursive binding cycle must be protected by a lambda after parameter desugaring. Unrestricted cyclic values such as `ones = 1 :: ones` are rejected; delaying computation requires an explicit function. More permissive strict recursion needs initialization-safety analysis: [A Practical Mode System for Recursive Definitions](https://doi.org/10.1145/3434326) shows how call-by-value languages can safely admit more recursive definitions. Ficus deliberately uses the smaller restriction described in [SPEC](SPEC.md).

## Predictable module loading instead of computed globals

By default, every top-level value initializer and implementation-member initializer must be non-expansive, even outside a recursive cycle and even with a complete signature. Literals, functions, constructors, and aggregates of non-expansive values remain available. General calls are rejected at top level under this default, including pure computations such as `answer = 40 + 2`. Computation and mutable-reference allocation belong inside functions or local bindings evaluated when those functions run.

This limits work during module loading and prevents modules from acquiring mutable state through arbitrary initialization calls. It also gives up convenient computed global constants and module-level reference allocation; callers must arrange any shared state explicitly. An immediately evaluated `where` group cannot bypass the restriction. Written parameters defer their attached `where` work until application, preserving the existing initialization timing. Non-expansiveness is a syntactic discipline, not a claim that every rejected expression has effects.

Go illustrates the flexibility Ficus gives up: package variables can have computed initializers, and `init` functions run before `main`, under specified dependency and ordering rules. See the [Go specification's initialization rules](https://go.dev/ref/spec#Package_initialization). A real standard-library example is [net/http/pprof](https://pkg.go.dev/net/http/pprof): importing it for side effects registers profiling handlers with the default HTTP server mux. That makes instrumentation convenient, but importing the package changes shared process state. Ficus instead requires such registration or allocation to happen through an explicit call during execution; importable Ficus modules do not offer arbitrary effectful initialization.

The v1+ standalone exception permits expansive acyclic top-level initialization in a module that cannot be imported. This allows computed globals and initialization-time state while keeping that work out of reusable library loading. Recursive groups and implementation members retain their restrictions, as do generalization rules. Standalone status does not select an entry or require main.

Execution explicitly selects one entry module, which must define its own valid `main`. Library modules need no entry point, and `main` functions in other modules are not automatically invoked. This avoids entry discovery depending on the modules loaded, at the cost of requiring the caller or tool to select an entry. Argument, reporting, and exit-status conventions remain open.

Python offers a familiar operational comparison: `python file.py` or `python -m package` explicitly selects what to execute. Its [official `__main__` documentation](https://docs.python.org/3/library/__main__.html) recommends guarding script-only work so importing a module for reuse or testing does not trigger that work; `python -m venv` is a standard-library example. Ficus makes the selected module's `main` a checked entry-point requirement, whereas Python's `main` function and guard are conventions and other module-level code can still execute on import.

## Effects and proofs: knowing where to stop

I haven't seriously read any effects papers yet, so this is a scope decision, not a grand verdict on algebraic effects. Ficus uses strict evaluation and direct effects; if handlers are what you're after, try [Koka](https://koka-lang.github.io/koka/doc/book.html).

Ficus is also not intended to be a theorem prover. It wants to run your script, not defend your dissertation. For dependent types and proofs, please use [Lean](https://lean-lang.org/doc/reference/latest) or [Agda](https://agda.readthedocs.io/en/stable/) instead. Planned exceptions and mutable references do not turn Ficus into an algebraic effect system—or a proof assistant.
